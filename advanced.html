dxrun (source: dx_rt/cli/dxrun.cpp; legacy alias: run_model) loads one .dxnn model straight onto the NPU and measures its raw performance — the model-level number, independent of any application logic around it.

dxrun(소스: dx_rt/cli/dxrun.cpp, 레거시 별칭: run_model)은 .dxnn 모델 하나를 NPU에 직접 로드해 순수 성능을 측정합니다. 주변 애플리케이션 로직과 무관한 모델 레벨 수치입니다.

dxrun（源码：dx_rt/cli/dxrun.cpp；旧别名：run_model）将单个 .dxnn 模型直接加载到 NPU 上，测量其原始性能，即不受外围应用逻辑影响的模型级数值。

dxrun（ソース：dx_rt/cli/dxrun.cpp、レガシーエイリアス： run_model）は、1 つの .dxnn モデルを NPU に直接ロードして、 その素の性能を測定します。周辺のアプリケーションロジックに依存しない、モデルレベルの数値です。

dxrun (mã nguồn: dx_rt/cli/dxrun.cpp; alias cũ: run_model) nạp trực tiếp một model .dxnn lên NPU và đo hiệu năng thuần, tức con số ở mức model, không phụ thuộc vào logic ứng dụng bao quanh.

2.1 Throughput tối đa (benchmark mode)

Benchmark mode (-b) is the default when none of --single, --fps > 0, or --max-throughput is given. It pushes the NPU to its maximum sustainable throughput with a fixed --buffer-count (default 6).

벤치마크 모드(-b)는 --single, --fps > 0, --max-throughput을 지정하지 않았을 때의 기본 모드입니다. 고정된 --buffer-count(기본값 6)로 NPU를 지속 가능한 최대 처리량까지 끌어올립니다.

未指定 --single、--fps > 0 或 --max-throughput 时，benchmark 模式（-b）为默认模式。该模式以固定的 --buffer-count（默认 6）让 NPU 达到可持续的最大吞吐量。

--single、--fps > 0、--max-throughput のいずれも指定しない場合は、 ベンチマークモード（-b）がデフォルトです。固定の --buffer-count（デフォルト 6）で、 NPU を持続可能な最大スループットで動作させます。

Benchmark mode (-b) là chế độ mặc định khi không chỉ định --single, --fps > 0 hay --max-throughput. Chế độ này đẩy NPU lên mức throughput tối đa có thể duy trì, với --buffer-count cố định (mặc định 6).

DX-RT v3.5.0 adds a --max-throughput mode. It measures throughput across buffer counts and recommends the smallest --buffer-count within a tolerance (--sweep-tolerance, default 1%) of the peak. Add -t or -l and it goes on to benchmark at the recommended value. Before each measurement it waits until the NPU cools below --cool-down-temp (default 45°C), so it can take a few minutes. On this PC it recommended buffer-count 7 (338 FPS), slightly above the default of 6 (about 304–320 FPS).

DX-RT v3.5.0에 --max-throughput 모드가 추가되었습니다. 버퍼 개수를 바꿔 가며 처리량을 측정하고, 최고치 대비 허용 오차(--sweep-tolerance, 기본값 1%) 안에 드는 가장 작은 --buffer-count를 추천합니다. -t나 -l을 함께 지정하면 추천값으로 벤치마크까지 이어서 실행합니다. 측정마다 NPU 온도가 --cool-down-temp(기본값 45°C) 아래로 내려갈 때까지 기다리므로 몇 분이 걸릴 수 있습니다. 이 PC에서는 buffer-count 7(338 FPS)을 추천했으며, 기본값 6(약 304~320 FPS)보다 조금 높았습니다.

DX-RT v3.5.0 新增了 --max-throughput 模式。该模式在不同缓冲区数量下测量吞吐量，并推荐与峰值相差在容差（--sweep-tolerance，默认 1%）以内的最小 --buffer-count。同时指定 -t 或 -l 时，会接着使用推荐值进行基准测试。每次测量前会等待 NPU 温度降至 --cool-down-temp（默认 45°C）以下，因此可能需要几分钟。本机推荐的 buffer-count 为 7（338 FPS），略高于默认值 6（约 304~320 FPS）。

DX-RT v3.5.0 では --max-throughput モードが追加されました。バッファ数を変えながらスループットを測定し、ピークから許容範囲 （--sweep-tolerance、デフォルト 1%）内に収まる最小の --buffer-count を推奨します。-t または -l を付けると、続けて推奨値でベンチマークを実行します。各測定の前に NPU 温度が --cool-down-temp（デフォルト 45°C）を 下回るまで待機するため、数分かかる場合があります。この PC では buffer-count 7（338 FPS）が推奨され、デフォルトの 6（約 304〜320 FPS）よりわずかに高い値でした。

DX-RT v3.5.0 bổ sung chế độ --max-throughput. Chế độ này đo throughput với nhiều giá trị buffer count khác nhau và đề xuất --buffer-count nhỏ nhất có throughput nằm trong ngưỡng sai lệch (--sweep-tolerance, mặc định 1%) so với giá trị đỉnh. Nếu thêm -t hoặc -l, lệnh sẽ tiếp tục chạy benchmark với giá trị đề xuất. Trước mỗi lần đo, lệnh chờ đến khi NPU nguội xuống dưới --cool-down-temp (mặc định 45°C), nên có thể mất vài phút.   • NPU Processing Time (7.172 ms) is only the time the NPU core itself spends computing — it excludes moving data to/from the device, and it barely changes from loop to loop.
  • Latency (14.475 ms) is the core latency excluding buffer-pool and queue waits, about 7.3 ms above the NPU Processing Time. This is the key thing -s tells you: when there is no pipelining at all — no next request queued up while the current one is still finishing — this is the honest, worst-case throughput ceiling for a single stream of strictly sequential requests on one NPU core. It is far below the multi-hundred-FPS numbers from benchmark mode, and that's expected: benchmark mode overlaps many in-flight requests across all 3 cores to hide exactly this transfer/format-handling overhead, while -s deliberately refuses to.

  • NPU Processing Time（7.172 ms）仅为 NPU 核心本身的计算时间，不含与设备之间的数据传输时间，各循环之间几乎不变。
  • Latency（14.475 ms）是不含缓冲池和队列等待的核心延迟，比 NPU Processing Time 多约 7.3 ms。该差值与 2.3 节 profiler 表中直接显示的各项之和（约 7.4 ms）相符：H2D 传输（~1.5 ms）、D2H 传输（~2.3 ms）、NPU Output Format Handler（~2.4 ms），以及 --use-ort 在 CPU 上运行的后段图（CPU Task，~1.2 ms）。使用 -s 时没有其他并行请求来掩盖这部分开销，因此每个请求都会完整体现。
  • E2E Response Time（15.501 ms）在此基础上再加上队列等待（Queue Wait Time，~1 ms），即完整的往返时间。
  • FPS（63.86）基本等于 1000 / E2E Response Time（1000 / 15.501 ≈ 64.5）。这是 -s 给出的关键信息：在完全没有流水线的情况下（当前请求完成前，下一个请求不会提前排队），这就是一个 NPU 核心处理严格顺序的单路请求时，真实的最坏情况吞吐量上限。它远低于 benchmark 模式下数百 FPS 的结果，这在预期之中：benchmark 模式让多个请求在 3 个核心上重叠执行，正是为了掩盖这些传输/格式处理开销，而 -s 刻意不这样做。

  • NPU Processing Time（7.172 ms）は NPU コア自体が演算に費やした時間のみで、デバイスとのデータ転送は含みません。ループごとの変化はほとんどありません。

For many camera-based edge applications, maximum throughput is rarely how a model runs in production — a 30 fps camera feed doesn't need the NPU running flat-out, since inference demand is bounded by the input frame rate. 많은 카메라 기반 엣지 애플리케이션에서는 실제 운영 환경에서 모델을 최대 처리량으로 실행하는 경우가 드뭅니다. 추론 수요가 입력 프레임 속도로 제한되므로, 30fps 카메라 입력이라면 NPU를 최대로 가동할 필요가 없습니다. target-FPS 모드는 입력 속도를 고정 FPS로 제한하므로, 2.1에서 벤치마크한 것과 동일한 모델로 포화 부하가 아닌 상한을 둔 대표적인 부하에서의 지연시간과 안정성을 확인할 수 있습니다.

对许多基于摄像头的边缘应用来说，生产环境中的模型很少以最大吞吐量运行：30fps 的摄像头输入并不需要 NPU 全速运行，因为推理需求受输入帧率限制。target-FPS 模式将输入速率限制为固定 FPS，以便在 2.1 节基准测试过的同一模型上，检查有代表性的受限负载下的延迟和稳定性，而非饱和状态下的表现。

カメラベースのエッジアプリケーションの多くでは、本番環境でモデルが最大 スループットで動作することはほとんどありません。推論の需要は入力フレームレートで 制限されるため、30 fps のカメラ入力では NPU をフル稼働させる必要はありません。 target-FPS モードは入力レートを一定の FPS に制限し、2.1 でベンチマークしたものと まったく同じモデルで、飽和状態ではなく代表的な制限付き負荷でのレイテンシと 安定性を確認できます。

Với nhiều ứng dụng edge dùng camera, model hiếm khi chạy ở throughput tối đa trong môi trường thực tế: luồng camera 30 fps không cần NPU chạy hết công suất vì nhu cầu inference bị giới hạn bởi frame rate đầu vào. Chế độ target-FPS giới hạn tốc độ đầu vào ở một mức FPS cố định, cho phép kiểm tra latency và độ ổn định dưới tải tiêu biểu có giới hạn thay vì tải bão hòa, trên đúng model đã benchmark ở mục 2.1.

Target-FPS mode automatically activates whenever -f is greater than 0 and --single is not set — it's mutually exclusive with 2.2's single-core mode. Combine it with -v to see per-frame NPU processing time and latency.

Maximum-throughput benchmarking intentionally drives NPU utilization close to 100%. 벤치마크 실행 중 NPU 온도가 오르면, 먼저 워크로드가 최대 처리량 모드로 실행 중인지 확인하세요. 최대 처리량 벤치마크는 NPU 활용률을 의도적으로 100% 가까이 끌어올립니다. 실제 배포에 가까운 워크로드에서 발열 특성을 평가하려면 -f <목표 fps>를 사용하고, dxtop으로 활용률과 온도를 함께 확인하세요.

2.4 Giới hạn NPU core (-n, --npu)

-n / --npu restricts a run to a subset of the NPU cores inside one device — it does not change how many requests are pipelined, only which physical core(s) are allowed to execute them. This is a different axis from -d / --devices, which selects which device(s) (chips) to use in a multi-device system; -n then selects core(s) within each of those devices.

-n / --npu는 실행에 사용할 NPU 코어를 디바이스 하나 안에서 일부로 제한합니다. 파이프라이닝되는 요청 수는 바뀌지 않으며, 요청을 실행할 수 있는 물리 코어만 제한합니다. 이는 멀티 디바이스 시스템에서 사용할 디바이스(칩)를 선택하는 -d / --devices와는 별개의 축으로, -n은 선택된 각 디바이스 내부의 코어를 선택합니다.

-n / --npu 将运行限制在单个设备内的部分 NPU 核心上。它不改变流水线中的请求数量，只决定允许哪些物理核心执行这些请求。这与 -d / --devices 属于不同维度：后者在多设备系统中选择使用哪些设备（芯片），-n 则在这些设备内部选择核心。

-n / --npu は、実行に使う NPU コアを1 つのデバイス内の 一部に制限します。パイプライン化されるリクエスト数は変わらず、どの物理コアで 実行できるかだけが変わります。これは、マルチデバイス構成で どのデバイス（チップ）を使用するかを選択する -d / --devices とは別の軸です。-n は、選択した各デバイスの 内部でコアを選択します。

-n / --npu giới hạn lần chạy trên một tập con NPU core trong một thiết bị: tùy chọn này không thay đổi số request được pipeline, chỉ quyết định core vật lý nào được phép thực thi chúng. Đây là một chiều khác với -d / --devices, vốn chọn thiết bị (chip) nào được dùng trong hệ thống nhiều thiết bị; sau đó -n chọn core bên trong từng thiết bị đó.

# Restrict the run to NPU core 0 only — still pipelined (multiple
# in-flight requests), just confined to a single physical core
dxrun -m model.dxnn --use-ort -t 30 -n 1 -v

# Restrict to a pair of cores (NPU_0 + NPU_1), leaving NPU_2 completely
# free for another model or process
dxrun -m model.dxnn --use-ort -t 30 -n 4

When this matters 활용 사례 适用场景 重要になるケース Khi nào cần dùng

Multi-model deployments where each model gets a dedicated core (e.g. Model A pinned to NPU_0, Model B to NPU_1/2). -n lets you benchmark that exact core allocation in isolation — the throughput you measure is what Model A will actually get once the other cores are busy with Model B, not the inflated number you'd see if you let it use all 3 cores during the test. Confirm the binding took effect with -v or by watching dxtop — only the bound core(s) should show non-zero Util.

모델마다 전용 코어를 할당하는 멀티 모델 배포에 유용합니다(예: Model A는 NPU_0, Model B는 NPU_1/2에 고정). -n을 사용하면 해당 코어 할당 그대로 독립적으로 벤치마크할 수 있습니다. 이렇게 측정한 처리량은 테스트 중 코어 3개를 모두 사용해 부풀려진 수치가 아니라, 다른 코어가 Model B를 처리하는 상황에서 Model A가 실제로 얻는 처리량입니다. -v나 dxtop으로 바인딩이 적용되었는지 확인하세요. 지정한 코어만 Util이 0보다 커야 합니다.

适用于为每个模型分配专属核心的多模型部署（例如 Model A 固定在 NPU_0，Model B 使用 NPU_1/2）。使用 -n 可单独对这种核心分配方案进行基准测试：测得的吞吐量就是其他核心被 Model B 占用时 Model A 实际能获得的吞吐量，而不是测试时使用全部 3 个核心得到的虚高数值。可通过 -v 或观察 dxtop 确认绑定是否生效：只有被绑定的核心应显示非零 Util。

各モデルに専用のコアを割り当てるマルチモデル構成（例：Model A を NPU_0 に、 Model B を NPU_1/2 に固定）で有効です。-n を使うと、そのコア割り当て のみで単独にベンチマークできます。測定されるスループットは、他のコアが Model B で 使用されているときに Model A が実際に得られる値であり、テスト中に 3 コアすべてを 使わせた場合の過大な値ではありません。割り当てが有効になっていることは、 -v または dxtop で確認してください。割り当てたコアだけ Util が 0 より大きくなるはずです。

Triển khai nhiều model, trong đó mỗi model được gán một core riêng (ví dụ Model A gán cho NPU_0, Model B cho NPU_1/2). -n cho phép benchmark riêng đúng cấu hình phân bổ core đó: throughput đo được chính là throughput Model A thực sự có khi các core còn lại đang bận với Model B, chứ không phải con số bị đẩy cao khi cho phép model dùng cả 3 core trong lúc thử nghiệm. Kiểm tra việc gán core đã có hiệu lực bằng -v hoặc theo dõi dxtop: chỉ những core được gán mới có Util khác 0.

Stage có giá trị trung bình lớn và CoV cao (như Buffer Pool Wait ở trên) là chỗ cần xem đầu tiên khi tìm nguyên nhân latency không ổn định; còn stage có trung bình chỉ vài µs (như NPU Input Format Handler) thì ít ảnh hưởng dù CoV cao.

When you need to compare many models at once — instead of running dxrun one model at a time — dxbenchmark walks a whole directory of .dxnn models and produces a single, shareable HTML report.

如需一次比较多个模型，而不是用 dxrun 逐个运行，可使用 dxbenchmark：它遍历整个目录中的 .dxnn 模型，生成一份可分享的 HTML 报告。

dxrun でモデルを 1 つずつ実行する代わりに、多数の モデルを一度に比較するには dxbenchmark を使用します。.dxnn モデルの ディレクトリ全体を走査し、共有可能な HTML レポートを 1 つ生成します。

Khi cần so sánh nhiều model cùng lúc thay vì chạy dxrun cho từng model, dxbenchmark sẽ chạy toàn bộ model .dxnn trong một thư mục và tạo một báo cáo HTML duy nhất để chia sẻ.

# Run every model under models/ for 60 seconds each
dxbenchmark --dir models/ -t 60

# Recurse into subdirectories, sort by latency descending, 30 s per model
# (-t or -l is required; add -d '0,1' only on systems with 2+ devices)
dxbenchmark --dir models/ --recursive --sort latency --order desc -t 30

dxbenchmark ships in the DX-RT package (libdxrt-bin) and is installed as /usr/local/bin/dxbenchmark, so it runs straight from your PATH (a source build of DX-RT also puts it in dx_rt/bin/). Without -t or -l it only prints usage and measures nothing, so always give one of them, as in the second example. -d selects devices (chips), not cores: on a single-device system -d '0,1' fails with Device number 1 ... is larger than the number of available NPU(s): 1. Each model gets a 10-second warmup (--warmup) before measurement.

Up to dx_app v3.2.x, the thread that reads video frames and submits them to the NPU was also the thread that had to call cv::imshow/cv::waitKey for the preview window — so while it was busy drawing a window, it could neither read the next frame nor submit the next request.

dx_app v3.2.x까지는 영상 프레임을 읽어 NPU에 제출하는 스레드와 미리보기 창용 cv::imshow/cv::waitKey를 호출하는 스레드가 같은 스레드였습니다. 그래서 창을 그리는 동안에는 다음 프레임을 읽을 수도, 다음 요청을 제출할 수도 없었습니다.

在 dx_app v3.2.x 及更早版本中，读取视频帧并提交给 NPU 的线程，同时还要为预览窗口调用 cv::imshow/cv::waitKey。因此该线程忙于绘制窗口时，既无法读取下一帧，也无法提交下一个请求。

dx_app v3.2.x までは、動画フレームを読み込んで NPU に投入するスレッドが、プレビューウィンドウ用の cv::imshow/cv::waitKey を 呼び出すスレッドと同一でした。そのため、ウィンドウの描画中は、次のフレームの読み込みも次のリクエストの投入もできませんでした。

Đến dx_app v3.2.x, thread đọc frame video và submit lên NPU cũng chính là thread phải gọi cv::imshow/cv::waitKey cho cửa sổ preview. Vì vậy, khi thread này bận vẽ cửa sổ, nó không thể đọc frame tiếp theo hay submit request tiếp theo.

v3.2.x 的源码（common/runner/async_detection_runner.hpp）准确印证了这一点：其中叠加了两个相互独立的错误（以下说明针对 v3.2.x）：

v3.2.x のソースコード（common/runner/async_detection_runner.hpp）を見ると、このことが明確にわかります。2 つの別々の誤りが重なっていました（以下は v3.2.x についての説明です）：

Mã nguồn v3.2.x (common/runner/async_detection_runner.hpp) xác nhận chính xác điều này: có hai lỗi riêng biệt cộng dồn lên nhau (mô tả dưới đây áp dụng cho v3.2.x):

  1. The main loop calls the display poll itself. Every frame ends with if (!args.no_display && !pollDisplay()) break; — right inside the same for loop that does video >> frame and ie.RunAsync(...). There is no separate capture thread; reading, submitting, and polling the GUI all happen one after another, on one thread.
  2. 메인 루프가 디스플레이 폴링까지 직접 호출합니다. 모든 프레임 처리가 if (!args.no_display && !pollDisplay()) break;로 끝나는데, 이 코드가 video >> frame과 ie.RunAsync(...)를 수행하는 바로 그 같은 for 루프 안에 있습니다. 별도의 캡처 스레드가 없으므로 읽기·제출·GUI 폴링이 모두 한 스레드에서 차례로 실행됩니다.
  3. 主循环自行调用显示轮询。每一帧都以 if (!args.no_display && !pollDisplay()) break; 结束，该语句就位于执行 video >> frame 和 ie.RunAsync(...) 的同一个 for 循环内。没有独立的采集线程；读取、提交和 GUI 轮询都在同一个线程上依次执行。
  4. メインループ自体がディスプレイのポーリングを呼び出している。 すべてのフレームは if (!args.no_display && !pollDisplay()) break; で 終わります。これは video >> frame と ie.RunAsync(...) を 実行するのと同じ for ループの中です。専用のキャプチャ スレッドはなく、読み込み、投入、そして GUI のポーリングがすべて 1 つの スレッド上で順番に実行されます。
  5. Vòng lặp chính tự gọi display poll. Mỗi frame đều kết thúc bằng if (!args.no_display && !pollDisplay()) break;, nằm ngay trong cùng vòng for thực hiện video >> frame và ie.RunAsync(...). Không có capture thread riêng; việc đọc, submit và poll GUI đều diễn ra tuần tự trên cùng một thread.
  6. The GUI is polled twice per frame. pollDisplay() calls dxapp::showOutput(frame) and then calls cv::waitKey(1) again itself right after. The shared utility's own doc comment for showOutput() spells out why that's costly: "cv::waitKey() ignores its ms argument and always fully services the GUI event queue, so a duplicate call directly doubles per-frame display latency." — async_detection_runner.hpp never passes the pump_events=false flag that showOutput() provides specifically so callers can avoid this.
  7. GUI를 프레임마다 두 번 폴링합니다. pollDisplay()는 dxapp::showOutput(frame)을 호출한 직후 cv::waitKey(1)을 다시 직접 호출합니다. 공용 유틸리티 showOutput()의 문서 주석에 이것이 왜 비용이 큰지 명시되어 있습니다: "cv::waitKey()는 인자로 넘긴 ms 값과 무관하게 항상 GUI 이벤트 큐 전체를 처리하므로, 중복 호출은 프레임당 디스플레이 지연시간을 그대로 두 배로 늘린다." 그런데 async_detection_runner.hpp는 바로 이 중복 호출을 피하도록 마련된 pump_events=false 플래그를 한 번도 전달하지 않습니다.
  8. 每帧轮询 GUI 两次。pollDisplay() 调用 dxapp::showOutput(frame) 后，紧接着又自行调用一次 cv::waitKey(1)。公共工具函数 showOutput() 的文档注释明确说明了这样做的代价：“cv::waitKey() 会忽略传入的 ms 参数，始终完整处理一遍 GUI 事件队列，因此重复调用会直接使每帧的显示延迟翻倍。”然而 async_detection_runner.hpp 从未使用 showOutput() 专为避免此问题而提供的 pump_events=false 标志。
  9. GUI がフレームごとに 2 回ポーリングされている。 pollDisplay() は dxapp::showOutput(frame) を呼び出した 直後に、自身でも再度 cv::waitKey(1) を呼び出しています。共有 ユーティリティの showOutput() のドキュメントコメントには、 これが高コストである理由が明記されています：「cv::waitKey() は ms 引数を 無視し、常に GUI イベントキューを完全に処理するため、重複して呼び出すとフレームごとの 表示レイテンシがそのまま 2 倍になる。」async_detection_runner.hpp は、 呼び出し側がまさにこの問題を回避できるように用意されている pump_events=false フラグを一度も渡していません。
  10. GUI bị poll hai lần mỗi frame. pollDisplay() gọi dxapp::showOutput(frame), rồi ngay sau đó tự gọi thêm cv::waitKey(1). Chính comment tài liệu của showOutput() trong tiện ích dùng chung đã giải thích vì sao điều này tốn kém: "cv::waitKey() bỏ qua tham số ms và luôn xử lý hết hàng đợi sự kiện GUI, nên một lần gọi trùng lặp sẽ trực tiếp làm tăng gấp đôi độ trễ hiển thị mỗi frame." Tuy vậy, async_detection_runner.hpp không truyền cờ pump_events=false, vốn được showOutput() cung cấp chính là để người gọi tránh vấn đề này.

(v3.2.x measurements) By Little's Law, the serialization explains the FPS drop: ~6 inflight requests ÷ 0.0186 s = 323 FPS (without display) vs ~1.6 inflight ÷ 0.0135 s = 119 FPS (with display). The NPU isn't slower — it's starved: the capture thread is blocked servicing the GUI instead of feeding it work.

(v3.2.x 측정치) Little의 법칙으로 보면 이 직렬화가 FPS 하락의 원인입니다. display 없이는 inflight 요청 ~6개 ÷ 0.0186s ≈ 323 FPS, display를 켜면 ~1.6개 ÷ 0.0135s ≈ 119 FPS입니다. NPU가 느려진 것이 아니라 일감을 받지 못하는 상태입니다. 캡처 스레드가 GUI 처리에 묶여 NPU에 작업을 넣지 못합니다.

（v3.2.x 测量值）根据 Little 定律，这种串行化解释了 FPS 的下降：不显示时约 6 个 inflight 请求 ÷ 0.0186s ≈ 323 FPS，显示时约 1.6 个 ÷ 0.0135s ≈ 119 FPS。NPU 并没有变慢，而是处于饥饿状态：采集线程忙于处理 GUI，无法向 NPU 提交任务。

（v3.2.x での測定値）リトルの法則から、この直列化によって FPS の低下を説明できます。表示なしでは約 6 個の処理中リクエスト ÷ 0.0186 s ≈ 323 FPS、表示ありでは約 1.6 個 ÷ 0.0135 s ≈ 119 FPS です。NPU の処理が遅くなったのではなく、処理が供給されない状態（starved）にあります。キャプチャスレッドが GUI の処理でブロックされ、NPU に処理を供給できていません。

(Số đo trên v3.2.x) Theo định luật Little, việc tuần tự hóa này giải thích mức sụt FPS: ~6 inflight request ÷ 0.0186 s = 323 FPS (không hiển thị) so với ~1.6 inflight ÷ 0.0135 s = 119 FPS (có hiển thị). NPU không chậm đi mà bị thiếu dữ liệu: capture thread bị chặn để phục vụ GUI thay vì cấp việc cho NPU.

BEFORE (Bottleneck):
┌──────────────────────────────────┐
│  Single Thread                   │
│  Capture → Submit → GUI Poll     │ (sequential)
│  └─ All serialized, FPS drops    │ ~120 FPS
└──────────────────────────────────┘

         ↓ (patch for v3.2.x / built into v3.3.0+)

AFTER (Decoupled):
┌────────────────┐   ┌──────────────┐
│ Capture/Submit │   │ GUI Display  │
│    Thread      │   │   Thread     │
└────────────────┘   └──────────────┘
        │                   ▲
        └── [2-slot] ───────┘
             Queue
      (non-blocking)
      ~215 FPS (1.8x faster)
  • Give frame-reading/submitting its own thread, so the main thread does nothing but pump the display window.영상 읽기/제출을 별도 스레드로 분리해, 메인 스레드는 화면 창 갱신만 담당하게 합니다.为帧读取/提交分配专用线程，主线程只负责驱动显示窗口。フレームの読み込みと投入を専用のスレッドに分離し、メインスレッドは表示ウィンドウの処理だけを行うようにします。Tách việc đọc/submit frame sang một thread riêng, để thread chính chỉ xử lý sự kiện cho cửa sổ hiển thị.
  • Make the hand-off to that display thread a tiny 2-slot, drop-oldest queue — if the window falls behind, it just skips stale frames instead of blocking anything upstream.화면 스레드로 넘기는 큐를 2칸짜리 drop-oldest(오래된 프레임 버림) 큐로 만듭니다. 창이 뒤처지면 오래된 프레임을 건너뛸 뿐, 앞단을 막지 않습니다.将交给显示线程的环节设计为一个很小的2 槽、丢弃最旧帧队列：窗口跟不上时，直接跳过过期帧，不阻塞上游任何环节。表示スレッドへの受け渡しには、小さな2 スロットの drop-oldest（最も古いものを破棄）キューを使用します。ウィンドウの処理が遅れても、古いフレームをスキップするだけで、上流の処理はブロックされません。Dùng một hàng đợi nhỏ 2 slot, bỏ frame cũ nhất để chuyển frame sang thread hiển thị: nếu cửa sổ hiển thị chậm, frame cũ sẽ bị bỏ qua thay vì chặn các bước phía trước.
  • Pump the GUI event queue once per frame, not twice.GUI 이벤트 큐는 프레임당 두 번이 아니라 한 번만 처리합니다.每帧只处理一次 GUI 事件队列，而非两次。GUI イベントキューの処理は、フレームごとに 2 回ではなく1 回にします。Xử lý hàng đợi sự kiện GUI một lần mỗi frame thay vì hai lần.

dx_app v3.3.0 builds this approach into the official code. The pipeline (read and submit) runs on a worker thread, the main thread only services the window through DisplayPump (common/utility/display_pump.hpp), and GUI events are pumped once per tick. The hand-off slot to the display is one frame deep. The default is lossless: every frame is shown, so a slow window makes the pipeline wait for it. --drop-frames switches to lossy: stale frames are dropped and nothing upstream blocks. 5.2 Pipeline Multi-Object Tracking

Demo entry 6 inserts one more DEEPX plugin, dxtracker, right after dxpostprocess. Unlike every other block in this chain, dxtracker runs entirely on the CPU — it doesn't touch the NPU at all. It takes this frame's detection boxes plus everything it remembers about previous frames and outputs the same boxes with a persistent track ID attached, using the OC_SORT algorithm.

데모 항목 6번은 dxpostprocess 바로 뒤에 DEEPX 플러그인 dxtracker를 하나 더 추가합니다. 이 체인의 다른 블록과 달리 dxtracker는 전적으로 CPU에서 동작하며 NPU는 전혀 사용하지 않습니다. 현재 프레임의 검출 박스와 이전 프레임에서 기억한 정보를 함께 사용해 같은 박스에 지속적인 track ID를 붙여 출력하며, 알고리즘은 OC_SORT를 사용합니다.

演示项 6 在 dxpostprocess 之后再插入一个 DEEPX 插件 dxtracker。与该链路中的其他模块不同，dxtracker 完全在 CPU 上运行，不使用 NPU。它结合当前帧的检测框和此前各帧的记录，使用 OC_SORT 算法，输出附带持久 track ID 的相同检测框。

デモ項目 6 では、dxpostprocess の直後に DEEPX プラグイン dxtracker がもう 1 つ追加されます。このチェーンの他のブロックとは異なり、 dxtracker はすべて CPU 上で動作し、NPU はまったく使用しません。 現在のフレームの検出ボックスと、過去のフレームについて保持している情報をもとに、 OC_SORT アルゴリズムを使って、同じボックスに永続的な track ID を付けて出力します。

Mục demo số 6 chèn thêm plugin DEEPX dxtracker ngay sau dxpostprocess. Khác với mọi khối khác trong chuỗi, dxtracker chạy hoàn toàn trên CPU và không dùng đến NPU. Plugin này nhận các box detection của frame hiện tại cùng thông tin đã lưu từ các frame trước, rồi xuất ra chính các box đó kèm track ID cố định, sử dụng thuật toán OC_SORT.

gst-launch-1.0 urisourcebin uri=file://video.mp4 ! decodebin ! \
    dxpreprocess config-file-path=configs/YoloV5S_PPU/preprocess_config.json ! queue ! \
    dxinfer config-file-path=configs/YoloV5S_PPU/inference_config.json ! queue ! \
    dxpostprocess config-file-path=configs/YoloV5S_PPU/postprocess_config.json ! queue ! \
    dxtracker config-file-path=configs/tracker_config.json ! queue ! \
    dxosd ! queue ! videoconvert ! fpsdisplaysink sync=false

dxtracker doesn't just label boxes — it also filters them: an object that can't be reliably matched across frames is dropped rather than forwarded, so dxosd only ever draws boxes with a stable ID. Tuning lives entirely in configs/tracker_config.json (det_thresh, max_age, min_hits, …) — no model, no NPU involved, so retuning tracking behavior needs no recompilation and no re-inference.

dxtracker는 박스에 라벨만 붙이는 것이 아니라 필터링도 합니다. 프레임 간에 안정적으로 매칭되지 않는 객체는 전달하지 않고 버리므로, dxosd는 항상 ID가 안정적인 박스만 그립니다. 튜닝은 모두 configs/tracker_config.json(det_thresh, max_age, min_hits 등)에서 합니다. 모델과 NPU가 관여하지 않으므로 트래킹 동작을 다시 튜닝해도 재컴파일이나 재추론이 필요 없습니다.

dxtracker 不只是为检测框打标签，还会对其进行过滤：无法在帧间可靠匹配的目标会被丢弃，不再向下游传递，因此 dxosd 只绘制带有稳定 ID 的检测框。所有调优都在 configs/tracker_config.json（det_thresh、max_age、min_hits 等）中完成，不涉及模型和 NPU，因此调整跟踪行为既无需重新编译，也无需重新推理。

dxtracker はボックスにラベルを付けるだけでなく、 フィルタリングも行います。フレーム間で確実に対応付けできない物体は 後段に渡さずに破棄するため、dxosd が描画するのは安定した ID を持つボックスだけです。 調整はすべて configs/tracker_config.json （det_thresh、max_age、min_hits など）で行います。 モデルも NPU も関与しないため、トラッキング動作を再調整しても再コンパイルや再推論は不要です。

dxtracker không chỉ gắn nhãn cho box mà còn lọc chúng: đối tượng không thể ghép khớp ổn định qua các frame sẽ bị loại bỏ thay vì được chuyển tiếp, nên dxosd chỉ vẽ các box có ID ổn định. Mọi tham số tinh chỉnh đều nằm trong configs/tracker_config.json (det_thresh, max_age, min_hits, …); không liên quan đến model hay NPU, nên khi chỉnh lại hành vi tracking không cần biên dịch lại hay chạy lại inference.

5.3 Multi-Channel Object Detection (RTSP) — một pipeline NPU dùng chung

Demo entry 8 feeds 4 RTSP cameras into one tiled display. There are two ways to build this in dx_stream, and this entry picks the more advanced one: instead of 4 independent dxpreprocess → dxinfer → dxpostprocess chains (one per stream, demo entry 7), it merges all 4 channels through dxinputselector into one shared NPU pipeline, then splits the result back out with dxoutputselector.

데모 항목 8번은 RTSP 카메라 4대의 영상을 하나의 타일 화면에 표시합니다. dx_stream에서 이를 구성하는 방법은 두 가지이며, 이 항목은 더 고급 방식을 사용합니다. 스트림마다 독립적인 dxpreprocess → dxinfer → dxpostprocess 체인 4개를 두는 대신(데모 항목 7번), 4개 채널을 dxinputselector로 합쳐 NPU 파이프라인 하나를 공유하고, 결과를 dxoutputselector로 다시 나눕니다.

演示项 8 将 4 路 RTSP 摄像头输入汇总到一个平铺显示窗口。在 dx_stream 中有两种实现方式，该演示项采用较进阶的一种：不使用 4 条独立的 dxpreprocess → dxinfer → dxpostprocess 链路（每路一条，即演示项 7），而是通过 dxinputselector 将 4 路全部合并到一条共享的 NPU 流水线，再用 dxoutputselector 将结果重新拆分。

デモ項目 8 は、4 台の RTSP カメラの映像を 1 つのタイル 表示にまとめます。dx_stream でこれを構成する方法は 2 つあり、 この項目ではより高度な方法を使用しています。ストリームごとに独立した dxpreprocess → dxinfer → dxpostprocess チェーンを 4 つ用意する （デモ項目 7）代わりに、dxinputselector で 4 チャネル すべてを1 つの共有 NPU パイプラインに統合し、その結果を dxoutputselector で再び分割します。

Mục demo số 8 đưa 4 camera RTSP vào một màn hình hiển thị dạng lưới. Có hai cách xây dựng cấu hình này trong dx_stream, và mục này dùng cách nâng cao hơn: thay vì 4 chuỗi dxpreprocess → dxinfer → dxpostprocess độc lập (mỗi stream một chuỗi, như mục demo số 7), cả 4 kênh được gộp qua dxinputselector vào một pipeline NPU dùng chung, rồi kết quả được tách lại bằng dxoutputselector.

# From dx_stream/pipelines/rtsp/run_RTSP.sh (simplified: 4 RTSP sources)
src1 ! decodebin ! in.sink_0    src2 ! decodebin ! in.sink_1
src3 ! decodebin ! in.sink_2    src4 ! decodebin ! in.sink_3

dxinputselector name=in ! \
    dxpreprocess config-file-path=configs/YoloV5S_PPU/preprocess_config.json ! queue ! \
    dxinfer config-file-path=configs/YoloV5S_PPU/inference_config.json ! queue ! \
    dxpostprocess config-file-path=configs/YoloV5S_PPU/postprocess_config.json ! queue ! \
    dxosd ! dxoutputselector name=out

out.src_0 ! dxscale width=640 height=360 ! comp.sink_0   # ...src_1..3 likewise
compositor name=comp ! videoconvert ! fpsdisplaysink

Between dxinputselector and dxoutputselector, every buffer carries a DXFrameMeta with a _stream_id — that's how one physical NPU pipeline can process frames belonging to 4 different cameras and still hand each result back to the correct output. dxscale and compositor can't live inside that shared section (they need one stable resolution/format to allocate buffers against), so they sit outside it — one dxscale per output stream, after dxoutputselector has already split things back apart.

dxinputselector와 dxoutputselector 사이에서는 모든 버퍼가 _stream_id가 담긴 DXFrameMeta를 함께 전달합니다. 덕분에 물리적으로 하나인 NPU 파이프라인이 카메라 4대의 프레임을 처리하면서도 각 결과를 올바른 출력으로 되돌려 보낼 수 있습니다. dxscale과 compositor는 버퍼 할당에 고정된 해상도/포맷이 필요하므로 이 공유 구간 안에 둘 수 없습니다. 따라서 dxoutputselector가 스트림을 다시 나눈 뒤의 바깥 구간에 두며, dxscale은 출력 스트림마다 하나씩 배치합니다.

在 dxinputselector 和 dxoutputselector 之间，每个缓冲区都携带含 _stream_id 的 DXFrameMeta。正因如此，一条物理 NPU 流水线才能处理来自 4 台不同摄像头的帧，并将每个结果送回正确的输出。dxscale 和 compositor 不能放在这个共享区段内（它们需要固定的分辨率/格式来分配缓冲区），因此位于共享区段之外：每个输出流各有一个 dxscale，位于 dxoutputselector 将各路重新拆分之后。

dxinputselector と dxoutputselector の間では、すべての バッファが _stream_id を持つ DXFrameMeta を保持しています。 この仕組みにより、物理的に 1 つの NPU パイプラインで 4 台の異なるカメラのフレームを 処理しながら、各結果を正しい出力に戻すことができます。 dxscale と compositor は、バッファを確保するために安定した 1 つの 解像度/フォーマットを必要とするため、この共有区間の内部には配置できません。そのため、 これらは共有区間の外側に配置されます。dxoutputselector がストリームを再び分割した後に、出力ストリームごとに 1 つの dxscale を置きます。

Giữa dxinputselector và dxoutputselector, mỗi buffer đều mang một DXFrameMeta có _stream_id. Nhờ đó, một pipeline NPU vật lý duy nhất có thể xử lý frame của 4 camera khác nhau mà vẫn trả từng kết quả về đúng output. dxscale và compositor không thể nằm trong phần dùng chung này (chúng cần một độ phân giải/định dạng cố định để cấp phát buffer), nên được đặt bên ngoài: mỗi output stream có một dxscale, đặt sau dxoutputselector khi các stream đã được tách ra.

Two ways to go multi-channel — which one? 멀티채널 구성 방식 비교 多路处理的两种方式：选哪一种？ マルチチャネルを構成する 2 つの方法：どちらを選ぶか Chọn cách triển khai multi-channel

Demo entry 7 (plain "Multi-Channel Object Detection") gives each stream its own full dxpreprocess/dxinfer/dxpostprocess/dxosd chain, merging only at the compositor — 4 independent NPU pipelines running concurrently. That maximizes hardware utilization and is simpler to reason about per-stream, but the official dx_stream docs note it can put real memory pressure on larger models. The selector-based approach here uses one NPU pipeline instead — lighter on memory, at the cost of every stream sharing the same dxinfer queue. Per the docs: "the performance gain [of sub-pipelines] may be negligible compared to selector-based pipelines depending on the environment" — benchmark both for your actual channel count and model before committing.

데모 항목 7번(일반 "Multi-Channel Object Detection")은 스트림마다 완전한 dxpreprocess/dxinfer/dxpostprocess/dxosd 체인을 따로 두고 compositor에서만 합칩니다. 즉 NPU 파이프라인 4개가 독립적으로 동시에 실행됩니다. 하드웨어 활용도를 최대화하고 스트림별로 동작을 이해하기도 쉽지만, dx_stream 공식 문서에 따르면 모델이 크면 메모리 부담이 상당할 수 있습니다. 여기서 다룬 셀렉터 기반 방식은 NPU 파이프라인을 하나만 사용하므로 메모리 부담이 적은 대신, 모든 스트림이 같은 dxinfer 큐를 공유합니다. 문서 원문: "환경에 따라 서브파이프라인 방식의 성능 이점은 셀렉터 기반 파이프라인에 비해 미미할 수 있다". 실제 채널 수와 모델로 두 방식을 모두 벤치마크한 뒤 결정하세요.

演示项 7（普通的 “Multi-Channel Object Detection”）为每一路配置完整独立的 dxpreprocess/dxinfer/dxpostprocess/dxosd 链路，只在 compositor 处合并，即 4 条 NPU 流水线并发运行。这种方式能最大化硬件利用率，按路分析也更简单，但 dx_stream 官方文档指出，模型较大时可能带来明显的内存压力。本节基于 selector 的方式只使用一条 NPU 流水线，内存占用更低，代价是所有通道共享同一个 dxinfer 队列。文档原文：“视环境不同，[子流水线方式] 相比基于 selector 的流水线，性能提升可能微乎其微”。在做出选择前，请针对实际的通道数和模型，对两种方式分别进行基准测试。

デモ項目 7（通常の「Multi-Channel Object Detection」）は、 ストリームごとに完全な dxpreprocess/dxinfer/dxpostprocess/dxosd チェーンを持たせ、compositor でのみ合流させます。つまり、4 つの 独立した NPU パイプラインが並行して動作します。ハードウェアの利用率を最大化でき、 ストリームごとの動作も把握しやすくなりますが、dx_stream の公式ドキュメントでは、大きなモデルではメモリ負荷が実際に高くなる可能性があると 指摘されています。ここで紹介したセレクターベースの方法は、代わりに1 つ の NPU パイプラインを使用します。メモリ負荷は軽くなりますが、すべてのストリームが 同じ dxinfer キューを共有することになります。ドキュメントには 「環境によっては、[サブパイプライン方式の]性能上の利点は、セレクターベースの パイプラインと比べてわずかな場合がある」とあります。採用を決める前に、 実際のチャネル数とモデルで両方をベンチマークしてください。

Mục demo số 7 ("Multi-Channel Object Detection" thông thường) cấp cho mỗi stream một chuỗi dxpreprocess/dxinfer/dxpostprocess/dxosd đầy đủ riêng, chỉ gộp lại ở compositor, tức 4 pipeline NPU độc lập chạy đồng thời. Cách này tận dụng phần cứng tối đa và dễ phân tích theo từng stream, nhưng tài liệu chính thức của dx_stream lưu ý rằng nó có thể gây áp lực bộ nhớ đáng kể với các model lớn. Cách dựa trên selector ở đây chỉ dùng một pipeline NPU, tốn ít bộ nhớ hơn, đổi lại mọi stream phải dùng chung một hàng đợi dxinfer. Theo tài liệu: "mức cải thiện hiệu năng [của sub-pipeline] có thể không đáng kể so với pipeline dựa trên selector, tùy theo môi trường". Hãy benchmark cả hai cách với đúng số kênh và model thực tế trước khi quyết định.

5.4 Secondary mode — xếp tầng hai model trên các đối tượng đang được tracking

Demo entry 9 (Secondary Mode) is the most involved pipeline in dx_stream: it runs primary detection + tracking, then two independent secondary models on every tracked person — object classification and face detection — using GStreamer's own tee and DEEPX's dxgather.

데모 항목 9번(Secondary Mode)은 dx_stream에서 가장 복잡한 파이프라인입니다. 1차 검출+트래킹을 수행한 뒤, 추적된 사람마다 독립적인 2차 모델 2개(객체 분류, 얼굴 검출)를 실행하며, 여기에는 GStreamer의 tee와 DEEPX의 dxgather를 사용합니다.

演示项 9（Secondary Mode）是 dx_stream 中最复杂的流水线：先执行主检测 + 跟踪，再对每个被跟踪的人运行两个独立的二级模型（目标分类和人脸检测），这一过程借助 GStreamer 自带的 tee 和 DEEPX 的 dxgather 实现。

デモ項目 9（Secondary Mode）は、dx_stream の中で最も 複雑なパイプラインです。プライマリの検出とトラッキングを実行した後、GStreamer 標準の tee と DEEPX の dxgather を使って、追跡した各人物に対して 2 つの独立したセカンダリモデル（オブジェクト分類と顔検出）を実行します。

Mục demo số 9 (Secondary Mode) là pipeline phức tạp nhất trong dx_stream: chạy detection chính + tracking, sau đó chạy hai model secondary độc lập trên từng người được tracking (object classification và face detection), sử dụng tee của GStreamer và dxgather của DEEPX.

# From dx_stream/pipelines/secondary_mode/run_secondary_mode.sh (simplified)
... dxpreprocess ! dxinfer ! dxpostprocess ! dxtracker ! tee name=t

t. ! dxpreprocess preprocess-id=2 resize-width=224 resize-height=224 secondary-mode=true ! \
     dxinfer preprocess-id=2 inference-id=2 secondary-mode=true model-path=efficientnet-lite0_224x224.dxnn ! \
     dxpostprocess inference-id=2 secondary-mode=true library-file-path=libpostprocess_object_class.so ! \
     gather.sink_0

t. ! dxpreprocess preprocess-id=3 resize-width=640 resize-height=640 secondary-mode=true target-class-id=0 ! \
     dxinfer preprocess-id=3 inference-id=3 secondary-mode=true model-path=scrfd-500m_640x640.dxnn ! \
     dxpostprocess inference-id=3 secondary-mode=true library-file-path=libpostprocess_scrfd500m.so ! \
     gather.sink_1

dxgather name=gather ! dxosd ! videoconvert ! fpsdisplaysink

Every dxpreprocess/dxinfer/dxpostprocess in this pipeline needs a matching pair of preprocess-id/inference-id — mix them up across the 3 models running here (primary, classification, face) and you get silently wrong results, not a crash. dxgather only merges buffers whose PTS matches exactly across all its sink pads — it assumes every branch is duplicated from the same tee, so it cannot merge streams from different sources or reorder mismatched timestamps.

이 파이프라인의 모든 dxpreprocess/dxinfer/dxpostprocess는 preprocess-id/inference-id가 정확히 짝을 이뤄야 합니다. 여기서 실행되는 모델 3개(1차, 분류, 얼굴) 사이에서 ID가 섞이면 크래시 없이 조용히 잘못된 결과가 나옵니다. dxgather는 모든 sink pad에서 PTS가 정확히 일치하는 버퍼만 병합합니다. 모든 브랜치가 같은 tee에서 복제되었다고 가정하므로, 서로 다른 소스의 스트림을 합치거나 어긋난 타임스탬프를 재정렬할 수 없습니다.

该流水线中的每个 dxpreprocess/dxinfer/dxpostprocess 都需要一对相互匹配的 preprocess-id/inference-id。如果在此处运行的 3 个模型（主检测、分类、人脸）之间混用这些 ID，不会崩溃，而是悄无声息地输出错误结果。dxgather 只合并所有 sink pad 上 PTS 完全一致的缓冲区：它假定每条分支都由同一个 tee 复制而来，因此无法合并来自不同来源的流，也无法对不匹配的时间戳重新排序。

このパイプライン内のすべての dxpreprocess/dxinfer/ dxpostprocess には、preprocess-id/inference-id の対応するペアが必要です。ここで動作する 3 つのモデル （プライマリ、分類、顔）の間でこれらを取り違えると、クラッシュはせずに 誤った結果が気づかれないまま出力されます。dxgather は、 すべての sink pad でPTS が完全に一致するバッファのみを統合します。 すべてのブランチが同じ tee から複製されていることを前提と しているため、異なるソースのストリームを統合したり、一致しないタイムスタンプ を並べ替えたりすることはできません。

Mỗi dxpreprocess/dxinfer/dxpostprocess trong pipeline này đều cần một cặp khớp nhau preprocess-id/inference-id. Nếu nhầm lẫn giữa 3 model đang chạy (primary, classification, face), kết quả sẽ sai mà không có cảnh báo, thay vì gây crash. dxgather chỉ gộp các buffer có PTS khớp chính xác trên tất cả sink pad; plugin này giả định mọi nhánh đều được nhân đôi từ cùng một tee, nên không thể gộp stream từ các nguồn khác nhau hay sắp xếp lại các timestamp không khớp.
