Thực hành: benchmark toàn bộ quy trình object detection với YOLO26n

Instead of abstract commands, this guide follows one real model — the YOLO26n object detector (an Ultralytics model, compiled for the DEEPX NPU) — from download, to a live NPU dashboard with dxtop, to maximum throughput, to a representative 30 fps deployment test, all the way to a real application and a real video pipeline. The results shown in this guide are reference measurements. Exact values may vary depending on the host system, software version, and system configuration.

추상적인 명령어 나열 대신 실제 모델 하나(DEEPX NPU용으로 컴파일한 Ultralytics YOLO26n 객체 검출 모델)를 따라가며 다운로드, dxtop 실시간 NPU 대시보드, 최대 처리량 측정, 대표적인 30fps 배포 테스트를 거쳐 실제 애플리케이션과 비디오 파이프라인 실행까지 진행합니다. 이 가이드의 결과는 참고용 측정치이며, 정확한 수치는 호스트 시스템, 소프트웨어 버전, 시스템 구성에 따라 달라질 수 있습니다.

本指南不罗列抽象命令，而是以一个真实模型（Ultralytics 的 YOLO26n 目标检测器，已为 DEEPX NPU 编译）为主线：从下载模型，到用 dxtop 查看实时 NPU 仪表盘，再到测试最大吞吐量、进行有代表性的 30 fps 部署测试，最后延伸到真实应用和真实视频流水线。本指南中的结果均为参考测量值，具体数值可能因主机系统、软件版本和系统配置而异。

本ガイドでは、抽象的なコマンドを並べるのではなく、1 つの実際のモデル （DEEPX NPU 向けにコンパイルした Ultralytics の YOLO26n 物体検出モデル）を使って、ダウンロードから dxtop によるライブ NPU ダッシュボード、最大スループットの測定、 代表的な 30 fps でのデプロイテスト、さらに実際のアプリケーションと ビデオパイプラインまでを順に解説します。本ガイドに示す結果は参考測定値です。 実際の値はホストシステム、ソフトウェアバージョン、システム構成によって 異なる場合があります。

Thay vì đưa ra các lệnh chung chung, hướng dẫn này đi theo một model thực tế là YOLO26n, object detector của Ultralytics được biên dịch cho DEEPX NPU: từ khâu tải về, theo dõi NPU trực tiếp với dxtop, đo throughput tối đa, kiểm thử triển khai tiêu biểu ở 30 fps, cho đến chạy trong một ứng dụng thực tế và một pipeline video thực tế. Kết quả trong hướng dẫn này là số đo tham khảo; giá trị cụ thể có thể khác tùy host system, phiên bản phần mềm và cấu hình hệ thống.

Expected: a line reading Processing accelerators: DEEPX .... 2. Kiểm tra kernel driver đã được nạp

lsmod | grep dxrt

Expected: dxrt_driver and dx_dma. If they are missing, the driver is either not installed or failed to build and load. By far the most common cause: the host kernel was updated and the DKMS module was never rebuilt against it — everything worked yesterday and stopped after a reboot. Reinstalling the dxrt-driver-dkms package rebuilds it for the running kernel. dmesg | grep -i dxrt usually names the reason directly.

예상 출력: dxrt_driver와 dx_dma. 보이지 않으면 드라이버가 설치되지 않았거나 빌드/로드에 실패한 것입니다. 가장 흔한 원인은 호스트 커널이 업데이트되었는데 DKMS 모듈을 새 커널에 맞춰 다시 빌드하지 않은 경우로, 어제까지 잘 되다가 재부팅 후 갑자기 안 되는 전형적인 사례입니다. dxrt-driver-dkms 패키지를 다시 설치하면 현재 커널에 맞게 재빌드됩니다. 실패 원인은 대개 dmesg | grep -i dxrt에 그대로 나옵니다.

预期输出：dxrt_driver 和 dx_dma。如未显示，说明驱动未安装，或构建/加载失败。最常见的原因是主机内核已更新，但 DKMS 模块未针对新内核重新构建：昨天还正常，重启后就失效了。重新安装 dxrt-driver-dkms 软件包即可针对当前内核重新构建。dmesg | grep -i dxrt 通常会直接显示原因。

期待される出力：dxrt_driver と dx_dma。表示されない場合は、ドライバが未インストールか、ビルドまたはロードに失敗しています。最も多い原因は、ホストのカーネルが更新されたのに DKMS モジュールが再ビルドされていないことです。前日まで動作していたのに再起動後に動かなくなる、というのが典型的な症状です。dxrt-driver-dkms パッケージを再インストールすると、実行中のカーネル向けに再ビルドされます。原因は通常 dmesg | grep -i dxrt の出力に直接示されます。

Kết quả mong đợi: dxrt_driver và dx_dma. Nếu thiếu, driver chưa được cài hoặc build/nạp không thành công. Nguyên nhân phổ biến nhất: kernel của host đã được cập nhật nhưng module DKMS chưa được build lại cho kernel mới, tức là hôm qua vẫn chạy bình thường nhưng sau khi reboot thì ngừng hoạt động. Cài lại gói dxrt-driver-dkms để build lại module cho kernel đang chạy. dmesg | grep -i dxrt thường cho biết trực tiếp nguyên nhân.

Since DX-RT v3.5.0 the result has five lines. FPS is the headline number for this step (maximum throughput). NPU Processing Time is the time the NPU core actually computes, E2E Response Time is the full time from a request going in to its result coming out (data transfer and buffer/queue waits included), Queue Wait Time is the part of that spent waiting in the NPU/CPU task queues, and Latency is the core latency excluding buffer-pool and queue waits. In maximum-throughput mode many requests are in flight at once, so the E2E Response Time is much longer than the NPU Processing Time.

DX-RT v3.5.0부터 결과가 다섯 줄로 늘었습니다. 이 단계의 핵심 수치는 FPS(최대 처리량)입니다. NPU Processing Time은 NPU 코어가 실제로 연산한 시간, E2E Response Time은 요청이 들어가서 결과가 나올 때까지의 전체 시간(데이터 전송, 버퍼/큐 대기 포함), Queue Wait Time은 그중 NPU/CPU 작업 큐에서 대기한 시간, Latency는 버퍼 풀·큐 대기를 제외한 코어 지연시간입니다. 최대 처리량 모드에서는 여러 요청이 동시에 처리되므로 E2E Response Time이 NPU Processing Time보다 훨씬 깁니다.

自 DX-RT v3.5.0 起，结果共五行。FPS 是本步骤的核心指标（最大吞吐量）。NPU Processing Time 是 NPU 核心实际计算的时间；E2E Response Time 是请求从输入到输出结果的完整时间（含数据传输和缓冲区/队列等待）；Queue Wait Time 是其中在 NPU/CPU 任务队列中等待的时间；Latency 是不含缓冲池和队列等待的核心延迟。最大吞吐量模式下有大量请求同时处理，因此 E2E Response Time 远长于 NPU Processing Time。

DX-RT v3.5.0 以降、結果は 5 行で表示されます。FPS はこのステップの主要な指標（最大スループット）です。 NPU Processing Time は NPU コアが実際に演算している時間、E2E Response Time はリクエストの 投入から結果が返るまでの全体時間（データ転送とバッファ/キューの待ち時間を含む）、Queue Wait Time はそのうち NPU/CPU タスクキューで待機した時間、Latency はバッファプールとキューの待ち時間を除いたコアレイテンシです。 最大スループットモードでは多数のリクエストが同時に処理されるため、E2E Response Time は NPU Processing Time よりも大幅に長くなります。

Từ DX-RT v3.5.0, kết quả gồm năm dòng. FPS là chỉ số chính của bước này (throughput tối đa). NPU Processing Time là thời gian NPU core thực sự tính toán; E2E Response Time là toàn bộ thời gian từ khi request được gửi vào đến khi có kết quả (bao gồm truyền dữ liệu và thời gian chờ buffer/queue); Queue Wait Time là phần thời gian chờ trong hàng đợi tác vụ NPU/CPU; còn Latency là core latency, không tính thời gian chờ buffer pool và queue. Ở chế độ throughput tối đa, nhiều request được xử lý đồng thời nên E2E Response Time dài hơn nhiều so với NPU Processing Time.

Inference FPS 값을 3단계의 벤치마크 모드 최대 처리량과 비교해 보세요. 같은 NPU가 같은 작업을 수행한 결과입니다. Overall FPS는 실제 CPU 전/후처리가 더해지므로 같거나 조금 낮게 나옵니다. 입력을 지정하지 않으면 sample/img/sample_street.jpg 이미지 한 장을 300번 반복하며, --no-display를 지정하면 화면 출력용 Render 단계는 표에 나오지 않습니다.

将 Inference FPS 行与第 3 步测得的 benchmark 模式上限对比：两者是同一块 NPU 在执行相同的工作。由于加入了 CPU 上真实的前/后处理，Overall FPS 会相同或略低。未指定输入时，会将单张图片 sample/img/sample_street.jpg 重复处理 300 次；使用 --no-display 时，表中不会出现仅用于屏幕显示的 Render 阶段。

Inference FPS の行を、ステップ 3 のベンチマークモードの上限と比較してください。同じ NPU が同じ処理をしています。 Overall FPS は、CPU 上での実際の前処理・後処理が加わるため、同じかやや低くなります。入力を指定しない場合は、 1 枚の画像 sample/img/sample_street.jpg を 300 回繰り返し処理します。--no-display を指定すると、画面表示専用の Render ステージは表に表示されません。

So sánh dòng Inference FPS với giới hạn đo ở benchmark mode tại Step 3: cùng một NPU, cùng một khối lượng công việc. Overall FPS bằng hoặc thấp hơn một chút vì đã bao gồm pre/post-processing thực tế trên CPU. Khi không chỉ định input, ảnh sample/img/sample_street.jpg được lặp lại 300 lần; với --no-display, stage Render (chỉ dùng cho hiển thị) không xuất hiện trong bảng.
